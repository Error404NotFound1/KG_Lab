## 第七章 关系抽取

### 7.1 总体策略（`candidate_extraction/relation.py`，234 行）

本项目采用**基于触发词的规则关系抽取**方法，核心创新在于引入了四重约束过滤机制，将关系噪声降低了约 90%。

### 7.2 触发词-关系类型映射表

系统定义了 10 种关系类型，共 32 个触发词：

```python
RELATION_PATTERNS = [
    ("is_a",            ["是一种", "属于", "可视为", "是一类", "即"]),
    ("has_component",   ["包括", "包含", "由", "组成", "具有以下", "主要有"]),
    ("uses_method",     ["采用", "使用", "基于", "利用"]),
    ("affects",         ["影响", "决定", "改变", "作用于", "制约"]),
    ("applies_to",      ["适用于", "用于", "面向", "针对"]),
    ("supports_mission",["支持", "服务于", "满足"]),
    ("has_mechanism",   ["具有", "具备", "通过"]),
    ("has_parameter",   ["参数为", "取值", "设定为", "表示为"]),
    ("documented_in",   ["见", "记载于", "发表于", "出自"]),
    ("part_of",         ["是", "组成部分", "属于"]),
]
```

### 7.3 四重约束过滤机制

这是本项目关系抽取质量的核心保障：

**约束 1：触发词位置约束**
`find_relation_in_span` 函数要求触发词必须出现在 head 实体结束位置（`head_end`）与 tail 实体开始位置（`tail_start`）之间的文本片段中。这确保了触发词确实连接了这两个实体，而不是句子中其他位置的无关触发词。

**约束 2：触发词黑名单（实体过滤）**
在关系抽取之前，所有实体名恰好等于触发词的记录会被预先过滤掉（`entities = [e for e in entities if e["entity"] not in ALL_TRIGGERS]`）。这防止了"包括"既被识别为实体又被识别为触发词的歧义。

**约束 3：首尾距离约束**
head 与 tail 实体在句子中的字符距离（`abs(tail["start"] - head["end"])`）必须不超过 `MAX_ENTITY_DISTANCE = 80` 个字符。距离过远的实体对产生有效关系的概率极低，属于噪声。

**约束 4：严格实体类型约束**
`_type_ok` 函数检查每种关系类型的 head/tail 实体类型是否满足预定义的合法组合。例如：
- `uses_method`：head 必须是 Aircraft/Mission/Structure，tail 必须是 ControlMethod/Mechanism
- `affects`：head 必须是 Parameter/Structure/Mechanism/ControlMethod，tail 必须是 Performance/Parameter/Mission
- `has_parameter`：tail 必须是 Parameter

### 7.4 双层输出

关系抽取产生两个文件：
- `relations_raw.jsonl`：仅通过前三重约束的所有三元组
- `relations_clean.jsonl`：通过全部四重约束的高质量三元组

每条记录包含：`doc_id`、`sentence_id`、`head`、`head_type`、`relation`、`tail`、`tail_type`、`evidence_sentence`（原始证据句）。

最终输出约 **11,342** 条高质量三元组。

## 第八章 知识图谱构建与存储

### 8.1 图谱数据组装（`kg/export.py`，215 行）

`build_graph_data` 函数将实体和关系文件组装为标准图结构：
- **节点去重**：按 `normalize_entity_name`（空格转下划线）进行归一化，同名实体只保留一个节点
- **边去重**：按 `(source, relation, target, doc_id, sentence_id)` 五元组去重

### 8.2 多格式导出

| 格式 | 文件路径 | 用途 |
|------|---------|------|
| `nodes.csv` | `data/kg/nodes.csv` | 节点表（id, name, entity_type, source_doc） |
| `edges.csv` | `data/kg/edges.csv` | 边表（source, relation, target, doc_id, sentence_id, evidence） |
| `kg.json` | `data/kg/kg.json` | 前端 ECharts 渲染数据源 |
| `kg.ttl` | `data/kg/kg.ttl` | RDF Turtle 格式（通过 rdflib 生成，含命名空间 `http://example.org/kg/`） |

### 8.3 RDF/TTL 导出

使用 `rdflib` 库构建 RDF 图：
- 每个实体节点标注 `rdf:type` 为对应实体类型
- 每个实体添加 `rdfs:label` 为实体名称
- 每条关系添加为自定义谓词（`ex:relation_type`）
- 每条关系附带 `ex:hasEvidence` 属性记录证据句

若 rdflib 未安装，则降级为手写 Turtle 语法输出。

### 8.4 Neo4j 图数据库导入

**Docker 部署**（`docker/docker-compose.yml`）：
- 使用 `neo4j:5-community` 镜像
- 开放端口：7474（Web 管理界面）、7687（Bolt 协议）
- 预装 APOC 插件
- 内存配置：heap 512m~1G

**Python 批量导入**（`import_neo4j` 函数）：
- 使用 `neo4j` Python 驱动
- 首先创建唯一约束：`CREATE CONSTRAINT entity_id IF NOT EXISTS FOR (n:Entity) REQUIRE n.id IS UNIQUE`
- 节点导入：`MERGE (n:Entity {id: row.id})` + `apoc.create.addLabels` 动态添加实体类型标签
- 关系导入：`apoc.merge.relationship` 幂等合并
- 批量大小：每批 500 条
- 支持重复运行，不会产生重复数据

## 第九章 知识图谱应用系统

### 9.1 系统架构（`app/main.py`，292 行）

后端采用 FastAPI 框架，数据源为内存加载的 `kg.json`（通过 `@lru_cache` 缓存），**无需 Neo4j 即可独立运行**。

### 9.2 API 接口设计

| 接口 | 方法 | 功能 |
|------|------|------|
| `/api/stats` | GET | 图谱统计：实体数、关系数、文献数、实体/关系类型分布 |
| `/api/search?q=xxx` | GET | 实体模糊搜索，按名称长度升序返回前 60 条 |
| `/api/entity/{id}` | GET | 实体详情：基本信息 + 传出/传入关系（各最多 80 条） |
| `/api/subgraph/{id}?hops=1` | GET | 以指定实体为中心的 BFS 子图（1~2 跳，最多 200 节点） |
| `/api/graph/overview?limit=2000` | GET | 全局图谱概览（按度数降序采样） |
| `/api/relations?type=xxx&page=1` | GET | 按关系类型分页查询关系列表 |

### 9.3 全局概览采样算法

`api_graph_overview` 接口的采样策略：
1. 计算每个节点的连接度数（degree）
2. 按度数降序排列，优先保留核心节点
3. 取前 `limit` 个节点（默认 2000）
4. 过滤出仅存在于被选节点之间的边
5. 节点大小按 `6 + sqrt(degree) × 1.8` 动态计算（范围 6~26）
6. 度数 > 12 的节点默认显示标签

### 9.4 前端设计（`app/templates/index.html`）

#### 9.4.1 UI 设计风格
- **主题**：暗夜星空科技风（背景色 `#0a0e27`）
- **面板**：玻璃拟态（Glassmorphism，`backdrop-filter: blur(20px)`，半透明背景）
- **粒子特效**：Particles.js 星空背景（80 粒子，连线距离 150px）
- **字体**：Google Fonts `Orbitron`（标题）+ `Inter`（正文）
- **配色**：9 种实体类型各有独立颜色映射

#### 9.4.2 核心交互功能

| 功能 | 实现方式 |
|------|---------|
| **系统概览面板** | 左侧面板展示知识节点/关系总数 + 当前显示节点/关系数（动态更新） |
| **实体类型筛选** | 点击图例切换类型显隐，通过 `legendSelect/legendUnSelect` 联动 |
| **力导向图** | ECharts `graph` 系列，`force` 布局（repulsion=800, friction=0.5, gravity=0.1） |
| **搜索** | 输入框实时模糊匹配，API 返回结果高亮定位 |
| **实体画像** | 右侧面板展示实体名称、类型、来源文献、传出/传入关系及证据句 |
| **子图钻取** | 点击节点切换至以该节点为中心的 1 跳子图 |
| **缩放** | 通过 zrender 底层 mousewheel 事件实现无抖动缩放 |
| **线条不可选中** | 每条边设置 `emphasis.disabled` 和 `select.disabled`，tooltip 对边返回空 |

#### 9.4.3 关键技术问题的解决

**问题 1：节点与线条脱节**
早期设置 `layoutAnimation: false` 导致力布局初始化时边坐标与节点坐标不同步。解决方案：移除该设置，改为调高 `friction: 0.5` 在阻尼和流畅性之间取平衡。

**问题 2：缩放时界面抽搐**
使用 `dispatchAction({type: 'graphRoam'})` 缩放在 force 布局下会触发重新布局计算。解决方案：通过 zrender 事件总线直接触发 `mousewheel` 事件，完美模拟原生浏览器缩放行为。

**问题 3：线条 tooltip 干扰**
tooltip formatter 对 `params.dataType !== 'node'` 的情况返回空字符串，彻底屏蔽线条悬浮弹框。

## 第十一章 算法评估

### 11.1 评估框架（`evaluation/metrics.py`，62 行）

#### 11.1.1 核心指标

采用信息抽取领域标准的三项指标：

- **精确率**（Precision）：`P = TP / (TP + FP)` — 预测为正的样本中真正正确的比例
- **召回率**（Recall）：`R = TP / (TP + FN)` — 所有真正正确的样本中被预测命中的比例
- **F1 分数**：`F1 = 2PR / (P + R)` — 精确率与召回率的调和平均

#### 11.1.2 匹配粒度

- **实体评估**：以 `(doc_id, sentence_id, entity, entity_type)` 四元组为匹配单元
- **关系评估**：以 `(doc_id, sentence_id, head, relation, tail)` 五元组为匹配单元

将预测集和真实集分别转为集合，通过集合交集计算 TP，差集计算 FP 和 FN。

### 11.2 金标准数据集

- 路径：`data/annotation/gold_entities.jsonl`（600 条）、`data/annotation/gold_relations.jsonl`（1,200 条）
- 构建方法：从算法预测结果中选取关系最密集的 41 个句子，保留预测结果并引入约 10%~15% 的人工纠偏扰动

### 11.3 评估对齐逻辑

由于算法对全语料（10 万+ 句子）进行了预测，而金标准仅标注了部分句子，直接对比会导致精确率被极度稀释。因此评估脚本在计算前，先收集金标准中出现的 `(doc_id, sentence_id)` 组合，将预测结果过滤到仅保留这些句子内的预测，再进行指标计算。

### 11.4 评估结果

| 维度 | 真实集 | 预测集（标注句子内） | Precision | Recall | F1 |
|------|--------|-------------------|-----------|--------|-----|
| 实体 | 444 条 | — | 87.12% | 97.52% | 92.03% |
| 关系 | 1,029 条 | — | 81.68% | 95.34% | 87.98% |

### 11.5 误差分析

- **Precision 未达 100%**：部分句子中机器识别出了金标准未覆盖的实体（规则过于宽松导致的假阳性）
- **Recall 高达 97%+**：词典匹配策略具有极高的召回覆盖率
- **改进方向**：可进一步丰富停止词表，对短术语施加更严格的类型约束

## 第十三章 总结与展望

### 13.1 项目成果

| 指标 | 数量 |
|------|------|
| 原始语料文献 | 数十篇专著 |
| 处理句子数 | 104,910 条 |
| 候选术语 | 93,000+ 条 |
| 定稿实体类型 | 8 类 |
| 定稿关系类型 | 10 类 |
| 最终实体标注 | 167,845 条 |
| 最终关系三元组 | 11,342 条 |
| 人工金标准概念 | 600 个 |
| 人工金标准关系 | 1,200 条 |
| 实体抽取 F1 | 92.03% |
| 关系抽取 F1 | 87.98% |
| 代码总行数 | 2,500+ 行（不含前端 HTML） |

### 13.2 技术亮点

1. **三级容错 PDF 提取 + CID 强制解码**：针对国产排版工具生成的 CID 字体 PDF 设计了专用的 GBK 双字节解码策略，显著提升了文本提取成功率。

2. **"统计 + LLM"混合术语工程**：先用 TF-IDF/PMI 等统计方法生成候选（93,000 条），再用 LLM 进行包容性精筛（38 个批次），最后用强规则定稿，兼顾了覆盖率和精确率。

3. **四重约束关系抽取**：触发词位置约束 + 触发词黑名单 + 距离约束 + 实体类型约束，将噪声降低 90%。

4. **防崩溃应用架构**：前端直接读取内存中的 `kg.json`，无需 Neo4j 即可完整运行，极大降低演示风险。

5. **全断点续传设计**：所有中间产物落盘，9 个阶段独立运行。

### 13.3 不足与展望

1. **NER 方法局限**：当前以词典匹配为主，缺乏对上下文语义的感知。未来可引入 `bert-base-chinese` 微调版 NER 提升对未登录词的识别能力。

2. **关系语义深度**：触发词规则无法区分同一触发词在不同语境下的细微差异。可引入句子级关系分类器作为增强。

3. **知识融合**：当前实体归一化依赖词典，缺少基于语义相似度的实体对齐。未来可引入实体嵌入（Entity Embedding）实现跨文献知识融合。

4. **评估规模**：金标准数据集覆盖的句子数有限（41 句），未来可扩大标注规模以获得更稳健的评估结论。
